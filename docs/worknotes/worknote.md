### 2026-09-16 · M8 · Show-Harness 工程分析（完成）

- 目标：剖析 VLM 控制机器人机制，给出适配 ManiLoop 的工程方案，保持传感器赛道和独立评估边界。
- 变化：新增 [分析报告](../research/SHOW_HARNESS_ANALYSIS.md)，包含控制链路、输入与动作约定、插件、API 错误处理、微调与采集协议，以及文件职责、配置示例、里程碑和对照实验。README 增加入口；没有修改运行代码。
- 依据：上游固定提交 `137d5718c3b7af0150764d8f9beeb252c9f2794a`，论文 `arXiv:2609.10522v1`；对照 ManiLoop `e3fcb0e`。本次只读分析，没有执行上游机器人程序、下载模型或发送付费推理请求。
- 验证：核对论文架构图、主结果表和动作约定消融图；报告的 33 个固定源码文件链接与行号范围均在对应 checkout 检查通过，10 个仓库相对链接存在，JSON 示例可解析；私人路径与密钥格式扫描未发现问题。仅文档变更，不重新运行无关仿真测试。
- 难点与发现：上游零样本路径以计划结束置 success=true，微调真机路径则保留 success=false；解析失败可能沿用方向或默认下降；动作量、相机方向与训练模板具有特定平台约定。公开默认配置与论文部分设置不同，因此不能把默认运行当作论文复现。
- 经验／决策：优先验证“动作词—相机变化—实际运动”的一致性，复用现有 PoseTarget；先单动作，再消融规划、恢复与动作块。报告清楚区分源码事实、作者结果、上游测量和工程建议。
- 后续：按报告从图像／格式诊断、方向标定和九动作适配开始实施。尚未验证 Show-Harness 本机推理、语义策略在 LIBERO 的任务成功率或真机能力；本里程碑不代表这些功能已完成。

### 2026-09-16 · M7b · 独立聊天与供应商响应兼容（完成）
- 目标：让用户先配置并聊天，观察真实回复及失败原因，解除仿真状态对通信排障的干扰。
- 变化：新增 `maniloop chat` 与 `/chat`；手动／TOML／CC Switch 配置、模型选择、两种 API 协议、受控多轮聊天、超时和输出设置；显示 HTTP 状态、完成状态、脱敏错误、用量与部分正文。聊天不接触机器人、不写持久聊天日志、不自动重试。
- 真实验证：用户填写 FC 配置和 Key 后，`gpt-5.6-sol` / Responses 返回完整中文回复。页面中介绍能力的请求耗时 18.028 秒、4507 tokens；随后算术请求返回「连接成功，17 + 25 = 42」，耗时 9.842 秒、4543 tokens，HTTP 200、status=completed。只证明文字通信和对话流程，不代表图像、动作格式或任务能力已验证。
- 难点与修复：FC 返回空的 error code/message；OpenAI SDK 3.8.0 的 ResponseError 自动增加 `misalignment=None`。旧校验将 SDK 新增字段视为供应商额外错误字段，从而误报失败。真实 SDK 离线回归先复现失败，再改用 `model_dump(exclude_unset=True)` 仅校验线上实际提供字段；显式额外字段、非空错误与不完整响应继续拒绝。历史机器人日志未保存原始响应，不能证明其每次失败均由此造成。
- 验证：完整离线回归 142 项通过、13 项可选 LIBERO 检查跳过、58 项子测试通过；独立页面经本机模拟 HTTP 服务验证 Responses、Chat Completions 和不完整回复展示。没有为排查自动追加付费重试。
- 经验／决策：HTTP 成功、协议完整和动作可执行是不同层次；兼容性问题必须通过真实 SDK 反序列化测试，不能只用简单对象代替。网页使用纯文本渲染模型回复，Key 不进入日志和持久存储。
- 后续：保持当前聊天配置供用户继续测试；在修复后的机器人入口逐级验证图像和结构化动作，再评估任务成功率。模型列表失败不应阻止手填模型名称使用。

### 2026-09-16 · M7a · LLM 请求诊断与目标闭环（完成）
- 目标：实现已讨论的 P1/P2，让云端请求可诊断，并使一次 LLM 目标获得有界本地反馈执行。
- 变化：可调超时／推理强度和独立时间预算；文本、单图、双图动作格式三种诊断；失败耗时和脱敏类别、实际请求参数记录；终止场景在推理前重置；LLM 512 像素观测、固定目标位姿跟踪及执行终态反馈。CLI、网页和实验比较组同步。
- 验证：`MANILOOP_TEST_LIBERO=1 python -m pytest -q` 最终为 142 项测试、55 项子测试通过，包含 13 项真实 LIBERO 检查：小位移、旋转、512 像素渲染、夹爪保持与开合。本地 HTTP 模拟供应商的三种诊断全部通过，各一次调用、0/1/2 张图像、无物理步进。网页实际 +Z 10 mm 达到约 9.31 mm，位置残差约 0.74 mm。新版网页启动通过，双相机均为 512×512，初始仿真时间及 API 调用数为零。
- 远端验证：实现提交 `3ff9985` 的 [GitHub Actions](https://github.com/Daniel-rmc/ManiLoop/actions/runs/35051694421) 四项全部通过：Windows、macOS、Linux 离线测试，以及 Linux OSMesa 的双机器人渲染。
- 用户复测：新版服务中，Astra 约 58.65 秒、Sol 约 53.83 秒后收到未通过完整性检查的响应；供应商报告总 token 分别为 3038、3231。两次均为 0 个执行动作、0 秒仿真时间。这已不同于原先的客户端请求超时；当前日志仍不足以区分响应状态、非空 error 或 incomplete_details 中的具体问题，不能认定额度不足或模型操作失败。下一步先分层诊断，必要时补充经过允许列表过滤的响应状态／原因记录，保持不执行不完整动作。
- 难点与处理：低层 OSC 的增量必须针对固定目标重新计算；不能重复相同增量。目标完成要等待速度下降，避免经过目标便结束。初始化夹爪使用官方预热的零命令，避免首次移动顺带张开夹爪。超时用量未知时记录 null，批量报告不将未知用量计为零或重复累计同一请求；诊断和正式任务分开标记。诊断后手动调试恢复物理步进；夹爪停止需满足本体稳定条件，不能仅等待固定步数。
- 经验／决策：只改明确的 LLM 包装层，保留官方控制器／缩放／任务评分与 VLA 节奏；512 像素、执行器容差及真正生效的请求选项进入比较组。诊断得到动作也只展示，不执行。
- 后续：用户填写配置后依次进行文本、图像和动作格式诊断，再复测 FC 的小位移及正式任务；随后按固定任务与初始化集合评估真实云端成功率。流式诊断、结构化视觉辅助和训练模式仍为后续工作。

### 2026-09-16 · M7 · 云端运行诊断与 v2 设计（诊断完成）
- 目标：解释用户真实云端运行失败，判断动作接口是否适合高延迟 LLM，并形成可执行的改进顺序。
- 证据：第一次从已结束环境发出请求并立即停止；第二次首次请求约 47 秒后超时，动作数和控制步均为 0。默认请求超时为 45 秒。日志不足以进一步定位网关／网络／推理阶段，更不能将此例计为模型操作能力失败。
- 变化：新增 [诊断与 v2 设计](../design/LLM_LOOP_V2.md) 和 `scripts/diagnose_libero_control.py`，为文档提供可复现实验；生产控制协议尚未变更。
- 验证：独立官方 spatial task 0 / init 0 / seed 0，无渲染、无 API、无物体真值输入。要求 Z 轴上移 10 mm，单步实际 1.1003 mm；随后 19 步零增量最终 2.3495 mm；20 步本体反馈追踪同一目标最终 9.8278 mm，三维残差 0.1926 mm。这是控制器诊断，不是模型任务成功。
- 难点与处理：128×128 图像细节有限；一条云端动作只覆盖 0.05 秒，易把「接受设定值」误解成「到达目标」。请求失败的耗时记录和最终生效参数记录也不足。保留证据，将网络排障、控制语义和视觉表示分开验证。
- 经验／决策：LLM 宜选择有界短程目标，本地执行器依据传感反馈追踪固定目标；VLA 保留训练匹配的原生动作节奏。新增协议显式编号、分组比较；不能通过重复增量或读取真值隐藏地提高成功率。
- 后续：P1 请求诊断、生命周期和预算可见性；P2 LLM 图像配置与目标跟踪；P3 固定任务／初始化集合的真实模型评测。尚未复测 FC 请求、实现 v2 或验证云端抓取成功率。
